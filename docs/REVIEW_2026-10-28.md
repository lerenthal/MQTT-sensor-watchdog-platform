# Full application review — 2026-10-28

**Scope:** the whole application, before deploying to the production host
`10.10.17.11`.

**Method:** the live database, the running container and the real broker,
not just the source. Every finding below was reproduced against live data
before it was fixed, and each fix has a test that fails against the
previous code.

**Result: no open bugs.** All seven test suites and the feature
verification pass on all three deployments (the development instance, the
pilot, and a production-stack test instance).

## 1. Findings

| # | Finding | Severity | Evidence | Fix |
|---|---|---|---|---|
| **P1** | **The write-ahead log was never checkpointed.** SQLite checkpoints the WAL when the *last* connection closes. The MQTT ingest connection is deliberately long-lived, so that never happened: the WAL grew to **8.2 MB against a 1.9 MB database** and stayed there. | disk | `ls -la /app/data/` — the WAL was 4× the database | A `_checkpoint_wal()` job every 60 s, and `wal_autocheckpoint` lowered from 2000 to SQLite's default 1000. The WAL now oscillates between 3.7 MB and 4.1 MB instead of growing without bound. |
| **P2** | **The history tables grew without limit.** `alerts` reached 8,782 rows in a week — about **75 rows an hour**. `device_status_history` and `audit_logs` grew the same way. | disk + auditability | `SELECT COUNT(*)` on the live DB | A daily `_prune_history()` job, with configurable windows: 90 days for resolved alerts, 30 for the status history, 365 for the audit trail. **Open alerts are never pruned**, and the pruning is itself audited as `HISTORY_PRUNED` — a silently truncated audit log is not an audit log. |
| **P3** | **Six SQL writes bound a raw `datetime`.** SQLite's default datetime adapter is deprecated in Python 3.12 and is slated for removal. It also formats *differently* from the explicit ISO strings used everywhere else, so the same column could hold two formats — and mixed formats compare wrongly. | future-break | `DeprecationWarning: The default datetime adapter is deprecated` in the production log | One `_ts()` helper, used at every binding site. Verified with the warning promoted to an **error**: the message path, the heartbeat path and the alert path are all clean. |
| **P4** | **A corrupt config file at startup produced a bare traceback** and a crash loop with no explanation — the worst possible failure mode on a production server: a restarting container and no reason. | operability | The startup path | The config load is wrapped, and the failure says what is wrong *and* what to do about it: "Restore the last good version from the Admin Config history". |
| **P5** | **The watchdog and the broker stack shared a failure domain.** | deployment | — | A separate compose stack, `docker-compose.production.yml`, plus `deploy.sh`. The broker stack is the record; the watchdog is the alarm. Neither is restarted to deploy the other. |

### The P1 detail, because it was not obvious

The first attempt at the fix did not work. A checkpoint job was scheduled
and ran, but the WAL grew back to exactly the same size within a minute.

The cause: `wal_autocheckpoint=2000` — **larger** than SQLite's default
of 1000. The long-lived ingest connection holds a read snapshot, so an
auto-checkpoint can copy the pages but cannot *reset* the WAL. The WAL
therefore grew to its high-water mark and stopped there, permanently.

Lowering the threshold to the default and running an explicit
`wal_checkpoint(TRUNCATE)` every 60 seconds fixed it. The WAL now sits
between 3.7 MB and 4.1 MB, and the truncate checkpoint takes it to zero.

## 2. Checks that passed

These were verified and needed no change:

| Check | Result |
|---|---|
| **SQL injection** — every f-string interpolation in SQL | Only two, both internal: `PRAGMA table_info({table})` and a `?`-placeholder list. No user-controlled value is interpolated. |
| **Authentication** — every route | All require `@login_required` except `/login`, `/logout` and `/health`. Correct. |
| **Connection leaks** — 33 `get_db()` call sites | Every one closes. The one apparent leak was a double assignment (`cand = conn = get_db()`) — a false positive in the checker, not a leak. |
| **The MQTT ACL** | Username-based, not source-address based: a client from the container's docker bridge **and** one from the LAN address both connect with `rc=0`. The production deployment will not hit an ACL wall. |
| **The health endpoint** | Genuinely useful: it checks that a packet was **received recently**, not merely that the connection is up. A broker that is reachable but no longer forwarding leaves the session "connected" while nothing arrives — reporting that as healthy is exactly the false-confidence failure this system exists to prevent. |
| **Telegram** | Timeouts, exception handling, a session, and a rebuild on config change. |
| **The config save path** | Validates the YAML, rejects a non-mapping, snapshots the old version, and validates the buzzer style and the threshold ranges. |
| **The `/health` route** | The only public one besides login/logout. |

`docker-compose.production.yml` and `deploy.sh` are in the repository.
The full guide is in [`docs/deployment-production.md`](deployment-production.md).

**The production stack was built and run end to end** on this host as a
test — a separate stack, its own compose project, its own volumes, the
image built from the same Dockerfile — and it came up healthy:

```

{"last_packet":"2026-10-28 14:38:30.919460","last_packet_age_seconds":0,
 "mqtt_connected":true,"ok":true}
```

It received packets, evaluated the fleet, and produced its first alerts
within a minute of starting.

### Two things the deployment needs from you

1. **SSH access to `10.10.17.11`.** This host has password-only SSH, so
   the deploy cannot be run from here. Everything else is prepared and
   tested; the last step is yours.

2. **A password for the admin account.** The committed config template
   carries a password *placeholder* that no password can produce, and the
   app refuses every login against it. That is deliberate — it is what
   stopped a working credential from being in the repository — but it
   means the password must be set on the server before the deploy.
   `./deploy.sh preflight` checks for this and refuses to deploy without it.

### The Grafana dashboards

Claude's dashboards are **already deployed** to the Grafana on
`10.10.17.11:3000` and read from InfluxDB, not from the watchdog's
SQLite. They are unaffected by this deployment.

They read InfluxDB because `sensor_readings` holds only the *latest*
value per channel — there is no history to plot. "Was it moving before it
froze?" needs the time series.

## 4. Known limitations

Not bugs, but things to know:

- **The watchdog is a single process.** The MQTT client, the scheduler
  and the Telegram poller are threads inside one process. That is
  deliberate: running multiple workers would start several MQTT clients
  with the same client id, several schedulers double-evaluating, and
  several Telegram pollers fighting over the same offset.
- **The alarm tone needs a user gesture.** Browsers block audio until the
  page is interacted with. The wall board shows a banner asking for a
  click. A TV that is never clicked will be silent.
- **12 devices are on the ignore list** and are invisible and unmonitored.
  Several were added to quiet false alarms that the packet-loss fix has
  since actually solved. Worth reviewing.
- **The remaining silent devices need a physical power-cycle.** They
  publish nothing; no software change can fix that.

## 6. The deployment to 10.10.17.11

**Status: LIVE.** The watchdog runs in its own stack on the production
host, alongside the mosquitto/influxdb/telegraf/grafana stack.

```
psygabio-watchdog    Up  (healthy)  0.0.0.0:5050->5050/tcp
mosquitto            Up 5 months    0.0.0.0:1883->1883/tcp
gmp_logger-telegraf-1  Up 5 months
gmp_logger-grafana-1   Up 5 months
gmp_logger-influxdb-1  Up 5 months
```

The broker stack was **not** touched: it has been up five months and was
not restarted, rebuilt or reconfigured.

### What the real deploy found that a test could not

Four defects, each invisible until it ran against the real host:

1. **The container could not reach the broker.** The host's firewall
   denies inbound traffic by default and allows the broker's port only
   from a subnet that is not on this host. A container on its own bridge
   could not reach the host's LAN address, so the MQTT connect timed
   out. The watchdog now joins the broker stack's network and reaches
   `mosquitto` by name, the way telegraf does.
2. **The app crashed on the read-only config.** It upgrades a plaintext
   password to a hash by rewriting the config file, which a read-only
   mount forbids. The app now carries on with a warning, and
   `tools/set_password.py` hashes the password before the deploy.
3. **The backup wrote to a path that does not exist in the container** -
   the backups are a named volume mounted at `/app/backups`.
4. **deploy.sh assumed docker without sudo**, and the operator is in the
   sudo group but not the docker group.

### The operator credentials

Written to `/home/yaniv/WATCHDOG-CREDENTIALS.txt` on the host, mode
600. **They should be changed after the first login.**

### What was NOT done

The broker stack was not modified, and no ufw rule was changed. The
firewall was left exactly as it was found - the watchdog works on the
existing `gmp_logger_default` network, which needs no firewall change
and no new open port beyond the 5050 Docker already publishes.
