## 1. The headline problem

`airmon-1` was displayed like this:

| Device | Status | °C | RH% | CO2 |
|---|---|---|---|---|
| airmon-1 | **ONLINE** | 23.7 | 44.0 | 438 |

Three plausible numbers beside a green badge. In fact the **CO2 and humidity
readings were 2.3 days old** — the device's temperature channel was alive, so
the device looked healthy, while two of its three readings had been frozen
since 24 October. Nothing in the UI said so.

That is the precise failure this system exists to prevent (§7.1/§7.2 of the
original brief: "connected" and "receiving data" are different facts). It was
caused by the dashboard printing `devices.last_co2`, a denormalised column that
(a) is overwritten by whichever channel published last — so a device with two
CO2 channels flip-flops between two different readings — and (b) is **never
aged out**.

It now renders as `438` dimmed, with a `2.3d` badge and a tooltip giving the
channel name and exact timestamp. The value is still shown, because you asked
to still see CO2 on a CO2-stalled device; it simply can no longer masquerade as
current.

## 2. Findings and fixes

| # | Finding | Severity | Evidence | Fix |
|---|---|---|---|---|
| **C1** | **All DB timestamps were 2 hours wrong.** Every SQL write used SQLite `CURRENT_TIMESTAMP` (UTC) while all Python comparisons use local time (`Asia/Jerusalem`, UTC+2). | GMP / missed-alarm | Alerts showed `triggered_at 13:30:25` while the newest packet was `15:31:06`; container `date` = 15:31 IST, `date -u` = 13:31 | All writes now explicit local wall-clock; column defaults changed to `datetime('now','localtime')` |
| **C2** | **Stale readings rendered as live.** `last_temp/hum/co2` never age out and flip-flop on multi-channel devices. | missed-alarm | `airmon-1` CO2 198 273 s old (2.3 d) shown as a bare number; `maxim4` has 2 CO2 channels | Headline metrics derived from channels, with age, staleness, channel count |
| **C3** | **An out-of-range sensor paged every 30 s.** The device loop resolved `OUT_OF_RANGE` alerts it does not own; the range pass re-created them, so `_raise_or_nag` always saw "no active alert" and sent a fresh page. `nagging_interval_seconds` was bypassed. | false-alarm (severe) | Reproduced: a new alert row + a new page on every cycle — ~120 pages/hour from one sensor | Device loop now only resolves `OFFLINE/STALLED/SENSOR_SILENT/SUSPECTED_STALL` |
| **C4** | **Chronic flapping.** A single fixed staleness window cannot fit channels publishing on very different cadences. | false-alarm | **879** status changes in 12 h (portable-sense1: 237, airmon-1: 201); SYSTEMIC fired/cleared every ~15 min; 43 `OUT_OF_RANGE_CLEARED` rows, sht41-1 clearing every 1–2 min at 24.15 °C against a 24.0 limit | Per-channel adaptive staleness (EWMA of observed publish interval, `sensor_stale_interval_multiplier`, floor = `sensor_flatline_seconds`); clear-side deadband `out_of_range_clear_margin_pct` |
| **C5** | `/api/devices` opened a connection per poll **without closing it** and ran a status-history query **per device** (N+1, 31 round-trips/poll). | resource | fds on the DB in the live container crept 24 → 28 in 15 min | One grouped query; connection closed in `finally` |
| **C6** | Branding | — | — | Product name is now **PsygaBio Device Watchdog**, from `facility.app_name`, across header, browser tab and wall board |

### Why C1 matters most
It is not just cosmetic. The UTC/local mix:
- put the **GMP audit trail** two hours away from the device timeline — "who
  acknowledged this, and when" is exactly the question that must be answerable;
- **silently defeated the `OUT_OF_RANGE` dwell** added in the previous review:
  it computed `local now − UTC entered_at` ≈ offset + real elapsed, which is
  always past the threshold, so the hysteresis never gated anything. That is
  why the flapping persisted after the last round of fixes;
- made every channel look "frozen for 2 h" immediately after a restart, because
  the boot rebase wrote `last_change_ts` in UTC.

Historical rows keep their original (wrong) timestamps — rewriting an audit
trail would be worse than leaving it. Rows written from now on are correct.

## 3. Usability changes

- **Fleet summary strip** above the table: `online / offline / stalled /
  degraded / stale readings / out of range`, each a one-click filter (verified:
  clicking "stale readings" filtered 31 rows to the 1 affected device). Zero
  counts are dimmed so the eye lands on what is non-zero.
- **Readings show their age.** Stale values are dimmed with a compact age badge
  (`2.3d`, `15m`); out-of-range values are red; suppressed ones struck through.
  Tooltips give the channel name, exact timestamp and why it is flagged.
- **Multi-channel devices show `×N`** so it is obvious when a device has several
  CO2 or temperature channels and which one you are looking at.
- Units are stated (°C, %, ppm) and CO2 is shown as a whole number.

## 5. What I did not change

- **Historical timestamps** are left as written (see §2).
- **`sensor_flatline_seconds` stays 900 s.** With adaptive staleness it is now
  a floor rather than the whole rule, so it no longer needs raising.
- **Server-side flatline detection stays off.** The firmware's own
  `Value Stall` entity is now genuinely flowing (58 diagnostic rows, the B6 fix
  working live), which is the better signal.
- **The committed `config.yaml` now carries real password hashes** for
  `yaniv`/`operator` rather than placeholders — they were committed by an
  earlier automated rewrite. They are salted SHA-256, not plaintext, but they
  correspond to the known default passwords, so anyone with the repo can derive
  working credentials. Worth rotating. I did not change them because that would
  lock you out of the running instance without warning.

Two things to expect on that first restart:

1. **You will be logged out once.** The live `web.secret_key` is still the
   known `CHANGE_ME` default (38 chars), so the B4 fix regenerates it and
   persists a strong one — invalidating existing sessions. This also means the
   running instance is currently session-forgeable, so the sooner the better.
2. **A schema migration adds `sensor_readings.publish_interval_s`** (v9). It is
   additive and guarded; existing rows start with a NULL interval and simply
   use the floor until each channel has been observed twice.

Everything was verified against a **copy** of the live database on an isolated
port, never against production.

### Gaps the review left open — now closed

1. **The committed template carried working credentials.** `config.yaml`
   in git held salted SHA-256 hashes that crack instantly from `mushroom`
   and `operator` — the *live* passwords. Anyone with the repository could
   log in as admin. The template now carries a placeholder that no
   password can produce (`salt: ""`, `hash: "!"`), and the app **refuses
   every login attempt against a placeholder account**. A fresh install is
   unloggable-in until the operator sets a password.

2. **The timezone fix depended on the container's `TZ` env var.** SQLite's
   `datetime('now','localtime')` takes the timezone of the *process*. The
   live `docker-compose.yml` defaulted to `TZ: ${TZ:-UTC}` — so a
   container started without a `.env` would have written UTC again while
   the application believed it was local, and C1 would have silently
   returned. The app now **pins the timezone explicitly at startup**
   (from `facility.timezone` / `WATCHDOG_TZ`) and **verifies that
   SQLite and Python agree**, logging a `TIMEZONE MISMATCH` error if they
   do not. The compose default is `Asia/Jerusalem`, not UTC.

3. **The pilot config had no `facility.app_name`**, so the pilot would
   have used the fallback rather than the configured product name. Added,
   along with `facility.timezone`, to all three configs.
